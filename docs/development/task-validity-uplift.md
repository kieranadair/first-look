# Purpose, availability and defensible event tasks

First Look 0.5.0 · 24 November 2026 · task policy `2026-11-24.2`.

This release implements the seven agreed adaptations from Prior Labs' relational-prediction skill. The [plan](task-validity-plan.md) records scope and verification; the [research mapping](../research/task-validity.md) separates research, engineering guidance and application defaults. The skill is retained as reference material rather than executed as an agent workflow. First Look still takes one source table, runs entirely in Python on Community Cloud and uses optional hosted providers. No dependency was added.

## Source import and historical replay

The identifier inspection found a reproducible precision loss: two distinct decimal customer IDs above/at 2^53 could collapse after a missing cell forced numeric coercion to floating point. Recipe 2 preserves identifier-name strings, leading-zero codes and integer strings beyond the exact floating-point range before conversion. Long numeric identifiers are checked lexically, avoiding Python integer-conversion size limits. Already rounded values in an original numeric file cannot be recovered.

`source_inspection.py` profiles literal values before the missing-token policy. `NA`, `unknown`, 0, −1, 999 and placeholder dates are candidates with counts, not automatic nulls. Actual missing-token choices and parse failures remain distinct. Protected large integer strings can remain text; the app does not silently approximate them as measures or implement arbitrary-precision arithmetic.

The parser records `inference_version=2`. Reopening a historical bundle with no version uses recipe 1 and its original Parquet missing-token behavior, retaining the original context and values. Opening the same source as a new investigation uses recipe 2. Dataset source inspection is validated against supplied bytes when present; old bundles without it remain readable.

## Task and availability policy

Declarations live in the existing semantic metadata under `search.analytical_task` and `search.availability`. No new default semantic fields were added, preserving historical semantic hashes. Typed validation checks referenced field identities and timestamp roles. Saving a declaration uses the existing human assertion ledger and context invalidation. A population description documents intent; only actual source row membership filters data.

Prospective tasks need a target and a defined decision time or anchor. Availability distinguishes unreviewed, declared known-at-anchor, timestamp-plus-delay and unavailable. Known-at-anchor declarations bind to the decision-time/anchor basis; changing that basis requires review again. Timestamp rules compare each recorded value's availability against its row's anchor. A field with late or unknown timing is excluded as a whole from every model, rather than selectively passing it to a different provider. Undocumented mutable snapshots remain diagnostic assumptions or prospective exclusions; no historical value reconstruction is attempted.

Descriptive exploration remains available while these facts are unknown. Diagnostic models retain explicitly labelled availability assumptions. A prospective readiness result validates the declared protocol; it does not certify the source documentation, independence, generalization or causal interpretation. UTC arithmetic treats naive dates as a common UTC clock; users must review actual source time bases and reporting precision.

Text-derived features inherit the source availability, timestamp references, mutable/history restrictions and the mapped decision-time basis. The derived table retains a distinct schema/fingerprint and original-row mapping. Human confirmation of pre-outcome text availability remains required. Candidate predictor screening now uses the same training-only preparation path for both original and augmented runs.

## Model preparation and comparison

`model_protocol.prepare_model` performs stale-scope validation, target eligibility, complete-window filtering, bounded source selection, exact splitting, training-label availability purging, class support and predictor screening. The preview calls this same path without fitting. Target-dependent copy/component screens use training rows; preprocessing remains train-only. An independent test changes final held-out labels and verifies predictor decisions remain unchanged.

Ordinary protocols retain a 70/30 row/group/time holdout and existing declared group restrictions. A forward outcome horizon requires chronological evaluation on its anchor. Rows without complete forward coverage are omitted; training outcomes unavailable by the held-out boundary are purged. Ordinary chronological prospective tasks without outcome-knowledge timestamps retain an explicit training-label timing assumption; Event lab records and checks its separate reporting-delay bound. Preflight records labeled source rows, omitted windows, budget omissions, training/test IDs, partitions, predictors, exclusions and unresolved assumptions. Imports check agreement with the executed record.

The fixed estimator used for diagnostics is not chosen by final-test performance. Regression now retains both mean and median constant predictors. Each comparator's held-out predictions and local latency are recorded. An observed verdict compares the named diagnostic model with the strongest recorded alternative on the primary metric, without selecting a deployment winner or attaching significance. Text feature tables report the same estimator before/after augmentation on exactly matched memberships; a separate cross-estimator comparison cannot be attributed solely to representation.

## Event lab protocol

1. Select entity, event identity (or explicitly one event per recorded row), event timestamp and information-availability timestamp. Without the latter, explicitly attest that events were available at occurrence. Confirm observed events and complete recording through the selected coverage date.
2. Choose recurrence or event count, a past lookback and future horizon, and 3–6 chronological anchors at least one horizon apart. The lookback covers at least one horizon. Incomplete anchors are omitted; at least three complete, nonempty populations must remain.
3. For each anchor, select only entities with an event in `(anchor − lookback, anchor]` that was known by the anchor. Future-only entities cannot enter the population. Compute past counts, previous-window counts, active days and recency from available past events only.
4. Construct labels from `(anchor, anchor + horizon]`. Distinct event identities deduplicate repeated source rows; conflicting entity/time identities are rejected. Zero outcomes require the explicit coverage attestation. Events missing entity, event time or chosen identity block preparation because silently omitting them could create false negative labels. Unknown information-availability times exclude events from past features but retain their observed forward outcomes. An explicit 0–365-day outcome reporting-delay bound is checked against observed delays; training windows whose labels are not fully known by the final anchor are omitted. Repeated identities use the latest constituent availability time, or remain unknown if any is missing.
5. Preserve every derived row's original history/outcome memberships. The new CSV bytes, schema, semantic metadata and context are independent of the original source. Source values and the original group-holdout declaration are unchanged: this is an explicitly different task about later activity of observed entities.
6. Hold out exactly the last complete anchor; train only on earlier anchors whose outcome windows plus the declared reporting delay finish by that boundary. Evaluate once per frozen task, retaining local baselines and a previous-window comparator. Optional hosted TabPFN uses the same permitted features and exact held-out rows.

Limits: six anchors, 10,000 derived rows, 1–365 day windows, two preparations and two model evaluations per source context. Event work uses the existing two-worker manager, cancellation and stale-publication checks. No SQL generation, joins, hyperparameter search, spatial protocol, joint unseen-entity/time generalization, causal model or automatic follow-up completeness inference is supplied. Repeated entity anchors remain dependent; no independent-sample significance claim follows.

The synthetic **What happens next?** example contains explicit generator-supplied event coverage and information delay. It supplies no labels or predicted answers. The model comparison can expose a baseline outperforming a more complex estimator; that remains useful evidence rather than triggering automatic task tuning.

## Evidence, UI and validation

Understand exposes literal details as secondary inspection; Meaning places task and availability editors together; Models makes readiness visible before execution and leaves recorded protocol details secondary after fitting. Challenge keeps recording coverage beside its exact denominators. Event lab separates population/label inspection from model evaluation, keeping model metrics and chart diagnostics together. No authored CSS/JavaScript or new service was introduced.

Optional version-3 `analysis/event-tasks.json` carries frozen tasks, derived tables/memberships and model results. Data-free import validates and inspects saved derived values offline. Source-backed replay rebuilds populations/features/labels/memberships and verifies context/hash agreement, without provider calls. Exports and briefs include event tasks; prepared-download identity includes event state. Event/source values can be private even without original-file inclusion. Reference filter/return preserves event runs; meaning edits reset dependent work while immutable pins remain intact.

The full suite passes **300 tests**, including **40 new cases** (39 in `test_task_validity.py` and one added to the text-feature workflow suite). Lint, formatting, type checks and runtime-only packaging pass; the artifact contains 90 runtime files. New tests use independent exact identifier and event-window oracles, future-only perturbations, timing/mutable/basis restrictions, preflight/execution equality, training-only screening, frozen comparator membership, original/derived text availability, malformed event records, source/data-free replay and native page flows. The two pre-existing upstream pandas/NumPy resampling warnings remain visible; new duration arithmetic uses explicit units. Calendar-date coverage now aligns with timezone-aware observation clocks without discarding nanoseconds; regressions cover UTC and America/New_York. This fixes an ordinary discovery failure found while opening the UTC event example. Full DST-aware scheduling remains outside scope.

The real development agent API exercised event preparation, visible readiness, actual local fitting, held-out diagnostics, recording coverage, task/availability controls and evidence downloads without paid requests or screenshots. The report is regenerated at ignored `reports/task-validity-runtime.json`; repeat with `python -m scripts.task_validity_smoke`. See [development commands](README.md). GitHub/CI publication is distinct from observed Community Cloud deployment; no live provider quality or productivity effect is claimed.
